02 / Original diagram for this project

How our code turns data into evidence and predictions

Python runs the analysis inside .venv; VS Code is an optional editor and terminal. The workflow separates held-out predictions used to evaluate the method from the final models later applied to new queries. The second-stage models train on known enhancers, not the first stage’s predictions.

Read the software workflow as text
  1. prepare_data.py checks hashes, 200-base sequences, and S1 labels for 2,968 benchmark records. The contaminated historical test stays separate.
  2. build_features.py uses NumPy and RapidFuzz, S2 properties, and verified hg19 receipts to create 2,451 groups, fixed folds, and 4,105 PseKNC features per sequence.
  3. train_svm.py uses scikit-learn/LIBSVM and SciPy: five outer folds evaluate and three inner folds select settings. Related groups stay together. Held-out predictions, metrics, and audits are saved.
  4. A five-fold training-only search selects the final models. Layer I uses 2,968 records; layer II uses 1,484 known enhancers. Each model is fitted on its complete training set, and two final .npz files are saved.
  5. predict_svm.py accepts FASTA queries of exactly 200 A/C/G/T bases. It repeats the feature calculation with weight 0.1 for layer I and 0.4 for layer II. A layer-I score ≤0 produces non-enhancer; if >0, layer II produces strong for >0 or weak for ≤0.
  6. The CSV output retains the final class and local scores. Server comparisons use frozen predictions and do not feed back into parameter selection. No NEW_2026_DATA activity measurements enter these fits.

03 / A simple comparison

What we followed, what we changed, and why

Our code follows the paper’s two-stage idea. The main differences are how we rebuilt the software, how we test it, and the extra checks we added.

  1. The same prediction task and original data. We use the original 200-base benchmark sequences and their labels. Following the paper’s equations, we describe each sequence using short DNA-word frequencies and summaries calculated from a DNA-property table. Two SVM classifiers first identify enhancers, then distinguish strong from weak enhancers. These are the historical benchmark labels, not activity measurements in a particular cell type.

  2. We rebuilt the software from the paper. We have the paper, data, and supplements, but have not located the authors’ complete training code or recovered all original SVM settings. We wrote a Python implementation using scikit-learn’s LIBSVM-based classifier and documented choices where the description leaves uncertainty, such as how to count DNA words. Our saved models are trained by our code. Feature choices → · Training settings →

  3. A different test to reduce information leakage. The paper reported leave-one-out evaluation: testing one sequence at a time. We keep similar sequences and sequences from nearby genomic regions together, so related examples stay on the same side of each training/test split. We select model settings within the training portion only. This reduces the risk of an optimistic score from closely related examples appearing on both sides; it does not establish complete independence. A separate, later 400-sequence test contains 100 training duplicates and is used only as a diagnostic. Evaluation design and reasons →

  4. Extra checks to understand the reconstruction. We compared simpler DNA-word features, different scaling choices, and predictions from the authors’ server. These follow-up checks help us investigate which components matter and where predictions differ; they are additional experiments, not the original paper’s evaluation. Feature comparisons → · Server comparison →

What this means: our results describe a reconstruction tested with a different procedure. A higher or lower score alone does not establish that our software is better or worse than the authors’. Matching server predictions is a useful check, but exact reproduction remains unverified. The comparison with measured activity in HepG2, K562, and WTC11 is still planned.

Authors’ reference tool · access checked 19 October 2026

The authors’ iEnhancer-2L prediction tool

The Liu Lab iEnhancer-2L server is the web tool associated with the method of Liu et al. (2016). It accepts DNA sequences in FASTA format and returns enhancer or non-enhancer labels; predicted enhancers are classified as strong or weak. These predictions are not measurements of experimental activity.

Open the authors’ prediction tool ↗Usage instructions (ReadMe) ↗Original data and S1/S2 tables ↗

The ReadMe explains the input format, example sequences, submitting queries, and downloading results. We used this currently available server to compare its predictions with our saved models; the returned responses and screenshots are preserved with those results.

Prediction server available; complete author training code not located. The web interface provides predictions from the authors. Our scripts separately implement the paper’s equations. Current server access does not establish that its implementation or models are identical to those used in the 2016 evaluation.

Step 01 / Software

Install the tools and understand their roles

Git
Downloads the repository and records the code version. GitHub hosts the shared files; it does not run these local analyses.
Python + pip + venv
Python executes the scripts; pip installs their packages; venv keeps those packages isolated in .venv. The full workflow needs Python 3.12 or newer. The commands below use 3.13; the recorded runs used 3.14.3. A different Python or operating system is a new environment that must be recorded and checked.
VS Code + Microsoft Python extension
Optional interface for reading/editing files and running commands through Terminal → New Terminal. Install the extension from the Extensions panel. The same analysis works in a standalone terminal.
NumPy + RapidFuzz
NumPy 2.5.4 stores feature matrices and performs numerical calculations. RapidFuzz 3.14.6 measures sequence edit distances for grouping.
scikit-learn + SciPy
scikit-learn 1.9.1 supplies the LIBSVM-based SVC classifier and evaluation metrics; SciPy 1.18.1 supports numerical operations. The requirements file installs the recorded dependencies together. A separate LIBSVM installation is not needed for this implementation.

Hardware: the reconstruction runs on a CPU; no GPU is required. More workers use more memory. Commands use four workers; --workers 1 reduces parallel load. Later parameter comparisons can take considerably longer than preparing the data.

Version sources: requirements-training.txt and the saved environment lock. The paper used LIBSVM; matching a software library alone does not establish identical features, parameters, or evaluation.

Step 04 / Data audit

Prepare and check the labeled sequences

The preparation script checks the original file hashes against our reviewed copies, reads FASTA, verifies 200-base A/C/G/T sequences, joins the label crosswalk, and measures exact test overlap. It preserves the source files.

The commands use a new output/guide-run-01/ directory. If that run already exists, choose a new run name consistently in every command. Preparation and feature-building replace their derived files; training refuses a nonempty destination. Existing .venv environments can be activated without recreating them.

git rev-parse HEAD > replication/ienhancer_2l/output/guide-run-01/prepared/repository-commit.txt
python --version > replication/ienhancer_2l/output/guide-run-01/prepared/python-version.txt

Expected check: 2,968 benchmark sequences: 742 strong, 742 weak, 1,484 non-enhancers. Historical test: 400 records, with 100 exact training overlaps, all strong. This confirms data preparation only.

  • benchmark.csv: sequences, hashes, source pages, and labels. is_enhancer is 1 for strong/weak and 0 for non-enhancers. is_strong is 1 for strong, 0 for weak, and blank for non-enhancers.
  • legacy_test_diagnostic_only.csv: the later historical test, with an overlap flag; it remains separate from the benchmark.
  • data_audit.json: class counts, file hashes, and limitations. Outputs are under replication/ienhancer_2l/output/guide-run-01/prepared/, excluded from Git by default. Rerunning replaces these derived files, so each run needs to be archived before inputs change.
If a command fails

Python not found: the selected interpreter must be installed and the terminal reopened. File not found: the command requires the repository root as its working directory and the tracked data files to be present. Hash or label mismatch: processing must stop for comparison with the committed originals; changing expected hashes to bypass the check would invalidate it. Import error later: VS Code and pip must use the same environment.

Step 05 / Evaluation design

Decide what each result will mean before training

A fold is a portion of the data held aside while a model learns from the rest. In nested validation, inner folds select settings and outer folds estimate performance on examples unused by that selection.

Track A: historical reconstruction. Use S1's 2,968 examples for enhancer identification and its 1,484 enhancers for strength classification. The paper selected feature settings by 5-fold cross-validation, then reported jackknife (leave-one-out) results. A fixed-setting leave-one-out pass needs 2,968 + 1,484 fits; tuning adds more. A quick 5-fold trial is a debugging step, not a reproduced jackknife result.

Track B: a new grouped evaluation. All 2,968 sequence intervals were checked against hg19, using zero-based, end-exclusive coordinates. Records are connected if their intervals overlap or are at most 1,000 bases apart on the same chromosome, or if their 200-base sequences differ by at most 40 global edits in either orientation. Connected groups stay together in 5 outer folds and 3 inner folds, with seed 42 and balancing across the three classes. These are project choices, not the paper’s leave-one-out procedure or CD-HIT identity rule. They reduce specified leakage risks without proving complete independence. The policy, assignments, and checks are saved before training. Any scaler or tuning procedure must use only the relevant training folds.

The old 400-record test is unsuitable as independent evidence. Its 100 strong enhancers are already in training. Removing them leaves no strong class for strength evaluation. Exact matching alone also does not prove independence from related sequences. See the documented overlap findings.

Published feature choices were themselves selected using this benchmark. Holding those choices fixed is appropriate for reconstructing the published configuration, but it is not a fresh, fully independent estimate of the complete selection procedure. Report the two tracks separately. Cross-validation and grouped evaluation reference.

Step 06 / Implementation specification

Turn each sequence into 4,105 numbers

The feature extractor is implemented and tested against the equations and supplement, with unresolved author-code choices documented. PseKNC combines DNA word frequencies with sequence-derived structural descriptors. They are not measured chromatin or DNA-looping data.

Recorded interpretation: sample standard deviation reproduces S2’s normalized entries within their two-decimal rounding (maximum difference 0.004724). The primary reconstruction uses overlapping 6-letter windows and position-based dinucleotide pairs. Four additional variants preserve alternative counting, rounded-table and population-normalization choices; none has been selected by model accuracy.

python -m unittest discover -s replication/ienhancer_2l -p "test_*.py" -v
python replication/ienhancer_2l/build_features.py --prepared replication/ienhancer_2l/output/guide-run-01/prepared --receipts replication/ienhancer_2l/checkpoints/2026-10-13-groups-features/reference_receipts.json --output replication/ienhancer_2l/output/guide-run-01/features

The command uses saved reference receipts for an offline rerun. It writes fold assignments, audits, and five compressed matrix variants: 2,968 × 4,105 for layer I and 1,484 × 4,105 for layer II. Exact conventions, validation, output fields and fresh-reference commands →. No classifier is trained by this command.

  1. Transcribe the six columns in S2: Rise, Roll, Shift, Slide, Tilt, Twist, for all 16 dinucleotides. Preserve their labels, order, and source. Verify normalization across the 16 values per property using equation 9. Compare against S2's rounded normalized table and record the standard-deviation convention and precision.
  2. Count the 4,096 possible 6-letter DNA words in a fixed order and normalize the counts. Record the counting stride and treatment of end positions.
  3. For each distance j = 1…9, compute the average squared difference between the six normalized properties of dinucleotide pairs, following equations 7–8.
  4. Combine those nine correlation terms with the 4,096 frequencies using equation 6. Use w = 0.1 for layer I and w = 0.4 for layer II. Both use k = 6 and λ = 9 (equation 13).
The calculation, in compact notation
C(i, i+j) = mean over 6 properties of (P(D_i) - P(D_(i+j)))²
theta[j] = sum of C(i, i+j), i=1…L-j-1, divided by (L-j-1)
Z = sum(frequencies) + w * sum(theta)
features = [frequency / Z, …, w * theta[j] / Z, …]

L is sequence length; D_i is the dinucleotide indexed at position i; P is a normalized property value. The notation follows equations 6–8, subject to the indexing check below.

Resolve before calling this exact reproduction: the text near equation 6 and the Figure 2 caption say “non-overlapping,” while the L − j − 1 denominator uses position-based indexing. Recover an author implementation or reference feature vectors to settle the intended stride/indexing. Also settle use of rounded S2 values versus recomputed normalization and any subsequent feature scaling. Record an explicit interpretation if the original cannot be recovered; do not select one simply because it gives a higher score.

Acceptance checks: each vector has 4,105 finite, nonnegative entries and sums approximately to 1 under equation 6. Test a constant-base sequence (zero structural differences), a hand-calculated short example, and both weights. Check that input order never changes label alignment. Structural-property normalization is across the fixed property table; a separate model scaler, if used, must be fitted only on training data.

Step 07 / Model implementation

Train two separate SVM classifiers

  1. Layer I: use all 2,968 rows. Positive = enhancer (strong or weak); negative = non-enhancer. Build features with w = 0.1.
  2. Layer II: use only the 1,484 known enhancers. Positive = strong; negative = weak. Build features with w = 0.4.
  3. Use an RBF SVM and explicitly record C, gamma, scaling, class weights, solver tolerance, shrinking, software version, and score orientation. The paper describes grid search but does not provide the final C/gamma values in these materials. Scikit-learn's gamma="scale" is not a recovered paper setting.
  4. Search candidate settings using training-only validation. For a reconstruction attempt, record a predeclared logarithmic C/gamma search and every choice; do not tune against final test labels or repeatedly chase Table 1. A stricter nested evaluation must keep all selection inside each outer training fold.
  5. For each held-out example, save its ID, true label, predicted label, continuous decision score, and fold. For a new query, run layer II only if layer I predicts enhancer. Evaluate the paper's layer-II task on known enhancers separately from this end-to-end cascade.

The RBF kernel measures similarity between feature vectors. C controls the penalty for training errors; gamma controls how locally that similarity acts. Their values change predictions and must be recorded.

Start small: validate dimensions, labels, and score signs on a small debugging subset. Do not publish that subset's performance. Then run the full predefined protocol. The completed implementation uses the primary feature version without additional scaling. The parameter grid and selection rules were committed before fitting; all inner searches exclude the relevant outer-test groups.

Recorded protocol: 48 combinations of C and gamma, selected by mean inner-fold balanced accuracy; exact ties favor smaller C, then gamma. After the five outer evaluations, a separate five-fold search selects each full-data final model. Its selection score is not a new independent test result. Complete frozen protocol →

Step 10 / Optional prediction

Apply the saved models without training again

predict_svm.py loads the two final models from the committed checkpoint. Each FASTA query must contain exactly 200 A/C/G/T bases. The following runnable example uses the original enhancer file only to demonstrate the interface:

python replication/ienhancer_2l/predict_svm.py --fasta enhancer.cv.txt --output replication/ienhancer_2l/output/guide-run-01/training-sequence-demo.csv

This demonstration is not an evaluation: these sequences were used to train the final models. For a new query file, replace enhancer.cv.txt and choose a new output filename. The CSV reports a class and decision scores; scores are not probabilities or measured activity. Layer II is applied only after a positive layer-I prediction.
